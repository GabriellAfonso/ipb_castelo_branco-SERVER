# Phase 1 Data Model: Hymnal View History

Three new models in `features/songs/models/hymnal_history.py`, plus one derived structure that is
never stored. Nothing existing is modified.

**Weekday convention throughout: `0 = Monday … 6 = Sunday`** (Python's `datetime.weekday()`).
Sunday is `6`. See research R-11.

---

## HymnalViewEvent

One row per hymn view the app counted as real.

| Field | Type | Constraints | Notes |
|-------|------|-------------|-------|
| `client_event_id` | `UUIDField` | `unique=True`, required | Idempotency key, generated by the app |
| `hymn` | `FK(Hymn)` | `on_delete=PROTECT`, required, `related_name="view_events"` | History is never orphaned |
| `user` | `FK(settings.AUTH_USER_MODEL)` | `null=True`, `blank=True`, `on_delete=SET_NULL`, `related_name="hymn_view_events"` | Null = anonymous |
| `device_id` | `CharField(max_length=64)` | required | One UUID per app install |
| `viewed_at` | `DateTimeField` | required, `db_index=True` | Aware; sent by the app, not the sync time |
| `duration_seconds` | `PositiveIntegerField` | required | Stored as received — never re-validated (FR-011) |
| `app_version` | `CharField(max_length=32)` | `blank=True`, `default=""` | |
| `platform` | `CharField(max_length=32)` | `blank=True`, `default=""` | |
| `created_at` | `DateTimeField` | `auto_now_add=True` | When the server received it |

**Meta**
- `ordering = ["-viewed_at"]`
- `verbose_name = "hymn view event"`, `verbose_name_plural = "hymn view events"`
- `indexes`:
  - `("hymn", "device_id", "viewed_at")` — the write-time collapse candidate lookup
  - `("viewed_at",)` — reporting range scans
- `__str__` → `f"{self.hymn.number} @ {self.viewed_at:%Y-%m-%d %H:%M}"`

**Why `device_id` is `CharField(64)` and not `UUIDField`**: the app generates a UUID today, but the
backend must not reject a device whose install id format changes in a future app release —
`device_id` is an opaque key here, only ever compared for equality.

**Why `PROTECT` on hymn but `SET_NULL` on user**: deleting a hymn that has history would erase the
history; deleting a user must not (Edge Case: history must not shrink when someone leaves).

## ServiceWindow

A recurring weekly time range during which the church holds a service. Owned by this feature — not
read from `features/schedule`.

| Field | Type | Constraints |
|-------|------|-------------|
| `name` | `CharField(max_length=100)` | required, e.g. `"Culto de Domingo à Noite"` |
| `weekday` | `PositiveSmallIntegerField` | required, `0..6` (Monday..Sunday) |
| `start_time` | `TimeField` | required |
| `end_time` | `TimeField` | required, strictly after `start_time` |
| `active` | `BooleanField` | `default=True` |

**Meta**
- `ordering = ["weekday", "start_time"]` — also the tie-break for overlapping windows (FR-016:
  earliest-starting active match wins), so the ordering is behaviour, not cosmetics
- `verbose_name = "service window"`, `verbose_name_plural = "service windows"`
- `constraints`:
  - `CheckConstraint(condition=Q(end_time__gt=F("start_time")), name="service_window_end_after_start")`
  - `CheckConstraint(condition=Q(weekday__gte=0) & Q(weekday__lte=6), name="service_window_weekday_range")`
- `__str__` → `f"{self.name} ({self.weekday} {self.start_time}-{self.end_time})"`

**No midnight crossing**: `end_time > start_time` makes a window ending after 00:00 impossible by
construction. A late service would be modelled as two windows. Recorded in the spec's Assumptions.

**Seed migration** (`0006_seed_service_windows.py`, data migration with its reason documented at the
top per CLAUDE.md §5) — the church's **real** schedule, confirmed 2026-08-07:

| Name | Weekday | Start | End |
|------|---------|-------|-----|
| Terça de Oração | 1 (Tuesday) | 19:30 | 20:30 |
| Quinta de Oração | 3 (Thursday) | 19:30 | 20:30 |
| Escola Bíblica Dominical | 6 (Sunday) | 09:00 | 10:00 |
| Culto Dominical | 6 (Sunday) | 19:30 | 21:00 |

Uses `get_or_create` by name, so it is safe to re-run and never clobbers a window an admin already
created. Reverse deletes exactly these four by name, leaving later additions untouched.

These are the **scheduled** end times. Matching extends past them by `window_grace_minutes`, so a
hymn sung at 21:20 in a Culto Dominical still belongs to it.

The feature does not depend on this migration: with zero windows every view collapses by hymn plus
calendar day (FR-015).

## HymnalHistorySettings

Exactly one row, enforced by the database.

| Field | Type | Default | Accepted range |
|-------|------|---------|----------------|
| `min_seconds_to_count` | `PositiveIntegerField` | `30` | 1 … 3600 |
| `collapse_window_minutes` | `PositiveIntegerField` | `10` | 1 … 1440 |
| `max_batch_size` | `PositiveIntegerField` | `200` | 1 … 1000 |
| `max_past_days` | `PositiveIntegerField` | `90` | 1 … 3650 |
| `future_tolerance_minutes` | `PositiveIntegerField` | `5` | 1 … 1440 |
| `window_grace_minutes` | `PositiveIntegerField` | `30` | 1 … 1440 |

**Meta**
- `verbose_name = "hymnal history settings"`, `verbose_name_plural = "hymnal history settings"`
- `ordering = ["id"]`
- `constraints`: `CheckConstraint(condition=Q(id=1), name="hymnal_history_settings_singleton")`
- `__str__` → `"Hymnal history settings"`

**Upper bounds are validated at the serializer** (FR-026), not as database constraints: they are
sanity rails an admin should get a helpful message about, not invariants worth a migration when the
church wants a longer collapse window. The `id=1` constraint is the one that must be structural.

**Materialisation**: the repository's `get_settings()` does `get_or_create(id=1, defaults=...)`, so
a fresh database serves the defaults on first read without a data migration.

## Occurrence *(derived — never stored)*

Produced by the reporting service from events + active windows. This is the whole point of the
feature, so its identity rule is stated once here and referenced everywhere else.

**Identity (the collapse key)**:
- `(hymn_id, service_window_id, local_date)` when the event's local time falls inside an active
  window
- `(hymn_id, None, local_date)` when it falls inside none

**Fields**

| Field | Type | Source |
|-------|------|--------|
| `hymn_number` | `str` | `Hymn.number` |
| `hymn_title` | `str` | `Hymn.title` |
| `occurred_on` | `date` | local calendar date of the contributing events |
| `service_window_id` | `int \| None` | matched window, or `None` outside every window |
| `service_window_name` | `str \| None` | matched window's name, or `None` |
| `bucket` | `str` | grouping label, see below |
| `device_count` | `int` | distinct `device_id`s that contributed |

**Bucket label by `group_by`**

| `group_by` | Bucket format | Example |
|------------|---------------|---------|
| `service` | `"{ISO date}:{window id}"`, or `"{ISO date}:none"` outside every window | `2026-08-09:3` |
| `day` | `YYYY-MM-DD` | `2026-08-09` |
| `week` | `YYYY-Www` (ISO week) | `2026-W32` |
| `month` | `YYYY-MM` | `2026-08` |

`group_by` changes only the reported bucket — it never changes how occurrences collapse (FR-018).

**Matching algorithm** (pure function, unit-testable with no database):

```
for each event:
    local = to_local(event.viewed_at)                  # America/Sao_Paulo
    grace = settings.window_grace_minutes
    candidates = [w for w in active_windows
                  if w.weekday == local.weekday()
                  and start_of(local.date(), w.start_time)
                      <= local < start_of(local.date(), w.end_time) + grace]
    window = min(candidates, key=start_time) or None   # earliest-starting wins
    key = (event.hymn_id, window.id if window else None, local.date())
    accumulate device_id into key
```

Placement uses the event's start time only; duration never moves an event across buckets.

The comparison is built on datetimes rather than bare times so a grace period running past midnight
does not wrap to `00:xx` and silently stop matching. The start is never extended by the grace.

## Pydantic DTOs (`features/songs/hymnal_history_dtos.py`)

All extend `StrictBaseModel` (`extra="forbid"`), matching the project convention.

| DTO | Direction | Fields |
|-----|-----------|--------|
| `HymnViewEventInput` | view → ingest service | `client_event_id: UUID`, `hymn_id: int`, `device_id: str`, `viewed_at: datetime`, `duration_seconds: int`, `app_version: str = ""`, `platform: str = ""` |
| `RejectedEventDTO` | ingest service → view | `client_event_id: UUID`, `reason: str` |
| `IngestResultDTO` | ingest service → view | `accepted: list[UUID]`, `rejected: list[RejectedEventDTO]` |
| `OccurrenceDTO` | report service → view | the Occurrence fields above |
| `TopHymnDTO` | report service → view | `hymn_number: str`, `hymn_title: str`, `occurrence_count: int` |
| `HymnalHistorySettingsDTO` | both ways | the five settings fields |
| `ServiceWindowDTO` | both ways | `id: int \| None`, `name: str`, `weekday: int`, `start_time: time`, `end_time: time`, `active: bool` |
| `ReportRangeDTO` | view → report service | `from_date: date`, `to_date: date`, `group_by: str` |

`user` never appears in any outbound DTO — no per-person breakdown is exposed (spec: Out of Scope).
`device_id` is likewise internal; only the aggregate `device_count` leaves the service.

## Relationship to existing models

```
Hymn ──1:N──> HymnalViewEvent          (new, PROTECT)
User ──1:N──> HymnalViewEvent          (new, SET_NULL)

Song ──1:N──> Played                   (existing — untouched)
```

`Played` and `HymnalViewEvent` share no field, no foreign key and no code path. The only thing they
have in common is the domain they live in.
